# Incident: Postgres crashed (kill_db)

## Timeline (IST, 26 Oct 2026)
- ~23:36:30 first shop-api errors: "failed to resolve host 'postgres'"
- 23:37:22 PostgresDown fires (pg_up = 0)
- ~23:39:30 ShopHigh5xxRatio fires (5xx share passes 5% at ~23:38:30, rises to ~90%)
- ~23:39 p95 rises to ~9 s on all DB paths (ShopHighLatency likely fired as a side effect)
- 23:38 dashboard: postgres DOWN, shop-api UP, redis UP
- 23:46 deploys checked: newest tag deploy-20261026-165909 at 22:29, over an hour before the alert
- ~23:46:25 Postgres back; brief "Connection refused" and "the database system is starting up" errors
- 23:46:31 last error line; shop-api recovered without a restart

## Root cause
The Postgres container crashed (exit 137, killed). Every request needing the DB failed with 500 because the host `postgres` no longer existed on the Docker network.

## Evidence
- Dashboard: postgres DOWN while shop-api and redis stayed UP
- Logs: "failed to resolve host 'postgres'". Errno -2 (name not known) fails fast; Errno -3 (temporary failure in name resolution) waits for the DNS timeout, which pushed p95 to ~9 s
- No deploy near the alert, so it was infra, not code
- ShopApiDown did NOT fire: threads were not stuck waiting 30 s for a pool connection (unlike bad_pool_config), so /metrics kept answering
- RedisDown did NOT fire: Redis was healthy
- High p95 was a side effect of the DNS timeouts, not the cause
- Postgres's own logs show no shutdown message, which matches a crash, not a planned stop

## Time to diagnosis
~9 min (first alert 23:37 -> deploy ruled out 23:46). The DB was the obvious suspect within a minute from the "Is it up?" panel; most of the time went into finding how to check deploy times.

## Fix
Start Postgres again (`docker compose start postgres`). shop-api recovered by itself because pool_pre_ping replaces dead connections.

## Follow-up
- Postgres data survived (pgdata volume); no data loss expected because Postgres replays its write-ahead log (WAL) on restart.
